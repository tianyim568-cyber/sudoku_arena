# 第三部分：功能需求

## 3.1 用户管理模块

### 3.1.1 模块概述

负责系统中所有用户的认证与授权。MVP 阶段不提供用户注册功能，所有账号由管理员预先创建。

> 设计原因：正式比赛场景下，参赛选手是确定的，不需要开放注册。管理员创建账号可以确保选手身份的真实性和比赛资格的准确性。

### 3.1.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| UM-01 | 用户登录 | P0 | 全部 | 通过用户名和密码登录，获取 JWT Token |
| UM-02 | 用户登出 | P0 | 全部 | 清除 Token，断开 WebSocket |
| UM-03 | Token 校验 | P0 | 全部 | 每次请求携带 Token，后端校验有效性 |
| UM-04 | 角色权限校验 | P0 | 全部 | 根据角色限制可访问的 API 和页面 |
| UM-05 | 账号创建 | P0 | 管理员 | 管理员创建用户账号并分配角色 |
| UM-06 | 账号列表查看 | P1 | 管理员 | 查看系统中所有用户 |

### 3.1.3 功能详细说明

**UM-01 用户登录**

- 输入：用户名、密码
- 输出：JWT Token、用户 ID、角色
- 业务规则：
  - 用户名和密码不能为空
  - 用户名必须存在
  - 密码必须匹配
  - 登录成功后返回 Token，有效期 8 小时（可配置）
  - 登录失败返回统一的错误提示，不区分「用户名不存在」和「密码错误」（安全考虑）

> 安全原因：不区分用户名和密码哪个错误，防止攻击者枚举有效用户名。

**UM-05 账号创建**

- 输入：用户名、密码、角色
- 输出：创建的用户信息
- 业务规则：
  - 用户名不能重复
  - 密码最小长度 6 位
  - 角色只能是 ADMIN、JUDGE、PLAYER 之一
  - MVP 阶段密码以明文展示给管理员，由管理员通知选手（后续版本增加密码重置功能）

### 3.1.4 非功能约束

- Token 采用 JWT 标准，包含 userId、role、过期时间
- 密码存储使用 BCrypt 加密
- 同一账号不限制并发登录（MVP 阶段简化处理）

## 3.2 比赛管理模块

### 3.2.1 模块概述

负责比赛的全生命周期管理，包括比赛的创建、配置、轮次设置、题目绑定、队伍管理和选手分配。这些操作都在赛前完成。

> 设计原因：比赛管理是「赛前准备」的核心，将配置与执行分离，确保比赛引擎只需要关注流程执行，不需要关心配置细节。这是「配置与执行分离」原则的体现。

### 3.2.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| TM-01 | 创建比赛 | P0 | 管理员 | 创建一场新的比赛 |
| TM-02 | 编辑比赛 | P1 | 管理员 | 修改比赛基本信息（仅赛前可修改） |
| TM-03 | 查看比赛列表 | P0 | 管理员 | 查看所有比赛及状态 |
| TM-04 | 查看比赛详情 | P0 | 全部 | 查看单场比赛完整信息 |
| TM-05 | 创建轮次 | P0 | 管理员 | 为比赛添加轮次 |
| TM-06 | 配置轮次 | P0 | 管理员 | 设置轮次的赛制、时间、题目关联 |
| TM-07 | 导入题目 | P0 | 管理员 | 批量导入数独题目 |
| TM-08 | 查看题目 | P1 | 管理员 | 查看已导入的题目列表 |
| TM-09 | 创建队伍 | P0 | 管理员 | 创建参赛队伍 |
| TM-10 | 分配选手到队伍 | P0 | 管理员 | 将选手指派到具体队伍 |
| TM-11 | 分配裁判到比赛 | P0 | 管理员 | 为比赛指定裁判 |
| TM-12 | 比赛状态管理 | P0 | 管理员 | 查看和变更比赛状态 |

### 3.2.3 功能详细说明

**TM-01 创建比赛**

- 输入：比赛名称、描述（可选）、计划时间（可选）
- 输出：创建的比赛信息
- 业务规则：
  - 比赛名称不能为空，且在同一天不能重复
  - 创建后比赛状态为「待配置」（PENDING）
  - 自动创建对应的数据存储空间

**TM-05 创建轮次**

- 输入：轮次名称、赛制类型（ROUND1_NINE_ONE / ROUND2_RELAY / ROUND3_COLLABORATE）、比赛时长（分钟）
- 输出：创建的轮次信息
- 业务规则：
  - 一场比赛必须包含恰好 3 个轮次
  - 轮次有顺序编号（1、2、3）
  - 轮次必须在比赛开始前配置完成
  - 每种赛制类型对应不同的题目要求和计分规则

**TM-07 导入题目**

- 输入：轮次 ID、题目数据（JSON 或文件格式）
- 输出：导入结果（成功数量、失败数量、错误详情）
- 业务规则：
  - 第一轮需要恰好 10 道题（9 道 JOC + 1 道关联题）
  - 第二轮需要恰好 16 道题
  - 第三轮题目数量灵活（至少 1 道）
  - 每道题必须包含：初始棋盘状态、正确答案、分值
  - 第一轮前 9 道题还需包含：关联字母
  - 第一轮第 10 道题需关联前 9 道题的 ID

**题目数据结构（概念性描述，非代码）**

```
题目（Puzzle）:
  - id: 题目唯一标识
  - roundId: 所属轮次
  - type: 题目类型（JOC / STANDARD / FINAL）
  - initialGrid: 初始棋盘状态（81 个格子的数据）
  - solution: 正确答案（81 个格子的数据）
  - points: 分值
  - order: 在轮次中的顺序
  - letter: 关联字母（仅第一轮前 9 题使用）
  - relatedPuzzleIds: 关联题目 ID（仅第一轮第 10 题使用）
```

> 设计原因：题目数据结构设计需要兼顾三种赛制的不同需求。JOC 类题目需要额外的「关联字母」字段，关联题需要引用其他题目的 ID。使用统一的题目结构加上可选字段，而非为每种赛制设计不同的题目结构，降低了系统复杂度。

**TM-09 创建队伍**

- 输入：队伍名称、比赛 ID
- 输出：创建的队伍信息
- 业务规则：
  - 队伍名称在同一比赛内不能重复
  - 第二轮要求每队恰好 4 人，但队伍创建时不强制（分配时校验）
  - 队伍创建后处于「待分配」状态

**TM-10 分配选手到队伍**

- 输入：选手 ID、队伍 ID
- 输出：分配结果
- 业务规则：
  - 一个选手只能属于一场比赛中的一个队伍
  - 选手必须已存在且角色为 PLAYER
  - 第二轮比赛前校验每队是否恰好 4 人（如果未满足则无法开始第二轮）

## 3.3 比赛引擎模块

### 3.3.1 模块概述

比赛引擎是系统的核心模块，负责比赛进行时的所有流程控制。它协调其他模块完成三轮赛制的流程执行、计时管理、轮转逻辑和状态推进。

> 设计原因：将「流程执行」与「配置管理」分离是关键设计决策。比赛管理模块负责「赛前准备」，比赛引擎负责「赛中执行」。这使得引擎逻辑可以独立于配置方式，未来如果配置方式变化（如从手动导入变为自动生成），引擎不需要修改。

### 3.3.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| TE-01 | 开始比赛 | P0 | 裁判/管理员 | 触发比赛开始流程 |
| TE-02 | 开始轮次 | P0 | 裁判/管理员 | 触发指定轮次开始 |
| TE-03 | 暂停比赛 | P1 | 裁判 | 暂停当前轮次计时 |
| TE-04 | 恢复比赛 | P1 | 裁判 | 恢复当前轮次计时 |
| TE-05 | 结束轮次 | P0 | 系统/裁判 | 当前轮次计时结束或裁判手动结束 |
| TE-06 | 结束比赛 | P0 | 裁判/管理员 | 所有轮次完成后结束比赛 |
| TE-07 | 第一轮流程执行 | P0 | 系统 | 九九归一完整流程 |
| TE-08 | 第二轮流程执行 | P0 | 系统 | 轮转接力完整流程 |
| TE-09 | 第三轮流程执行 | P0 | 系统 | 齐心协力完整流程 |
| TE-10 | 服务器计时 | P0 | 系统 | 服务器端统一计时 |
| TE-11 | 题目轮转调度 | P0 | 系统 | 第二轮每分钟触发题目轮转 |
| TE-12 | 状态推送 | P0 | 系统 | 将比赛状态变更推送给所有客户端 |

### 3.3.3 功能详细说明

**TE-01 开始比赛**

- 前置条件：
  - 比赛已配置 3 个轮次
  - 每个轮次已导入足够的题目
  - 至少有 1 支队伍且每队至少 1 名选手
  - 已分配裁判
  - 所有选手已进入比赛房间（或裁判强制开始）
- 后置效果：
  - 比赛状态变更为「进行中」（IN_PROGRESS）
  - 通知所有客户端「比赛已开始」
  - 等待裁判触发第一轮

> 设计原因：「开始比赛」和「开始第一轮」是两个独立的动作。比赛开始是一个「就绪」信号，告知选手比赛即将开始。第一轮的实际开始由裁判控制，给裁判确认所有选手已准备好的时间窗口。

**TE-07 第一轮流程执行**

```
裁判触发「开始第一轮」
    │
    ▼
服务器将第一轮题目分发给所有选手
    │
    ▼
服务器启动 20 分钟倒计时
    │
    ▼
服务器每秒推送剩余时间
    │
    ▼
选手答题：
  ├── 填写格子 → 提交单题答案
  ├── 服务器验证答案
  ├── 正确 → 返回关联字母，更新分数
  └── 错误 → 返回错误提示
    │
    ▼
选手完成前 9 题，获取 9 个字母
    │
    ▼
选手解答第 10 题
    │
    ▼
倒计时结束 或 裁判手动结束
    │
    ▼
第一轮结束，推送结果
```

**TE-08 第二轮流程执行**

```
裁判触发「开始第二轮」
    │
    ▼
服务器将题目分配给各队队员（每队 4 人各 1 题，剩余 12 题入题池）
    │
    ▼
服务器启动 20 分钟倒计时
    │
    ▼
服务器启动轮转调度器（每分钟触发一次轮转）
    │
    ▼
循环：
  ├── 选手答题并提交
  │   ├── 服务器验证答案
  │   ├── 正确 → 更新分数，从题池分配新题
  │   └── 错误 → 返回错误提示（该题继续留在当前队员手中）
  │
  ├── 每分钟轮转
  │   ├── 所有未完成题目按 A→B→C→D→A 顺序轮转
  │   ├── 推送轮转事件，更新各队员看到的题目
  │   └── 保留题目上的已有填写状态
  │
  └── 每秒推送剩余时间
    │
    ▼
倒计时结束 或 裁判手动结束
    │
    ▼
第二轮结束，推送结果
```

**TE-09 第三轮流程执行**

```
裁判触发「开始第三轮」
    │
    ▼
服务器为每支队伍创建共享棋盘空间
    │
    ▼
服务器将第一道题分发给所有队伍
    │
    ▼
服务器启动 30 分钟倒计时
    │
    ▼
循环：
  ├── 队员填写格子 → 服务器验证并广播
  │   ├── 格子为空或自己占用 → 接受填写，广播给全队
  │   └── 格子已被其他队员占用 → 拒绝，通知该队员
  │
  ├── 队员提交完整答案
  │   ├── 正确 → 更新分数，推送下一题
  │   └── 错误 → 提示错误，继续当前题
  │
  └── 每秒推送剩余时间
    │
    ▼
倒计时结束 或 裁判手动结束
    │
    ▼
第三轮结束，推送结果
```

**TE-10 服务器计时**

- 计时由服务器端管理，使用 Java 的 ScheduledExecutorService
- 每秒计算剩余时间并推送
- 暂停时停止计时，恢复时继续
- 客户端仅展示服务器推送的时间，不得自行计算
- 计时精度：秒级（MVP 阶段足够）

> 设计原因：服务器权威计时是比赛公平性的基础。客户端网络延迟可能导致计时不同步，因此必须以服务器时间为准。每秒推送一次倒计时，在实时性和服务器负载之间取得平衡。V2 版本可优化为客户端本地倒计时 + 服务器定期校准，减少推送频率。

**TE-11 题目轮转调度**

- 第二轮开始时，服务器创建一个定时任务，每 60 秒触发一次轮转
- 轮转逻辑：
  1. 收集所有队伍中所有未完成的题目
  2. 对每支队伍，将未完成题目从当前队员转移到下一位队员
  3. 更新数据库中的题目-队员关联关系
  4. 推送轮转事件给所有受影响的队员
- 轮转与提交的优先级：如果队员在轮转前一刻提交了题目，该题已标记为完成，不参与轮转

> 设计原因：轮转逻辑是第二轮的核心，也是系统中最复杂的并发场景。使用服务器端定时任务统一调度，而非客户端触发，确保轮转时机的一致性。

### 3.3.4 比赛状态机

**比赛级别状态**

```
PENDING ──► READY ──► IN_PROGRESS ──► FINISHED
  │            │           │
  │            │           └──► PAUSED ──► IN_PROGRESS
  │            │
  │            └── 仅当所有配置完成后转换
  └── 仅当配置完成前
```

| 状态 | 说明 | 可转换到 |
|------|------|----------|
| PENDING | 刚创建，未配置 | READY |
| READY | 配置完成，等待开始 | IN_PROGRESS |
| IN_PROGRESS | 比赛进行中 | PAUSED, FINISHED |
| PAUSED | 比赛暂停 | IN_PROGRESS |
| FINISHED | 比赛已结束 | 无（终态） |

**轮次级别状态**

```
NOT_STARTED ──► IN_PROGRESS ──► FINISHED
                   │
                   └──► PAUSED ──► IN_PROGRESS
```

| 状态 | 说明 |
|------|------|
| NOT_STARTED | 轮次未开始 |
| IN_PROGRESS | 轮次进行中 |
| PAUSED | 轮次暂停 |
| FINISHED | 轮次已结束 |

> 设计原因：比赛和轮次各有独立的状态机，但轮次状态受比赛状态约束——比赛暂停时，当前轮次也必须暂停；比赛结束时，当前轮次也结束。这种双层状态机设计使状态管理更清晰。

## 3.4 房间管理模块

### 3.4.1 模块概述

管理比赛房间，即选手参与比赛的空间。每个比赛对应一个比赛空间，选手进入后可以看到比赛信息、等待开始、参与答题。

> 设计原因：将「空间管理」从「流程控制」中分离，是因为房间的生命周期（选手进入、等待、离开）和比赛的流程（开始、暂停、结束）是两个维度的关注点。分离后，房间管理可以独立演进（如 V2 增加房间聊天、房间设置等）。

### 3.4.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| RM-01 | 选手进入房间 | P0 | 选手 | 选手加入比赛空间 |
| RM-02 | 选手离开房间 | P0 | 选手 | 选手退出比赛空间（比赛中不允许） |
| RM-03 | 房间状态查询 | P0 | 裁判/管理员 | 查看房间内选手状态 |
| RM-04 | 房间人数统计 | P1 | 裁判/管理员 | 查看各房间在线人数 |
| RM-05 | WebSocket 连接管理 | P0 | 系统 | 管理选手的 WebSocket 连接 |

### 3.4.3 功能详细说明

**RM-01 选手进入房间**

- 前置条件：选手已登录，已被分配到该比赛的某支队伍
- 后置效果：
  - 选手的 WebSocket 连接到该比赛的通道
  - 其他房间成员收到「选手加入」通知
  - 裁判端更新选手在线状态

**RM-02 选手离开房间**

- 业务规则：
  - 比赛未开始时，选手可以自由离开
  - 比赛进行中，选手不允许主动离开（前端隐藏退出按钮）
  - 如果选手网络断开，服务器保持其答题状态，等待重连
  - 选手重连后，服务器推送当前比赛状态，选手可继续答题

> 设计原因：比赛中不允许选手主动离开是比赛严肃性的体现。但网络断开是不可避免的，系统需要支持断线重连。MVP 阶段的重连策略是：服务器保持状态，选手重连后恢复到断线前的状态。这比「断线即弃权」更公平。

**RM-05 WebSocket 连接管理**

- 选手进入房间时建立 WebSocket 连接
- 维护「用户 ID → WebSocket Session」的映射
- 心跳检测：客户端每 30 秒发送一次心跳，服务器 60 秒无心跳则判定断线
- 断线后标记选手状态为「离线」，但保留答题数据
- 重连后恢复选手状态为「在线」

## 3.5 实时同步模块

### 3.5.1 模块概述

基于 WebSocket 的实时通信层，负责服务器与客户端之间的双向消息传递。是所有实时功能的基础设施。

> 设计原因：将实时通信抽象为独立模块，使得业务模块（比赛引擎、房间管理等）不需要关心消息传输的细节。如果未来需要替换 WebSocket 为其他协议（如 SSE、gRPC），只需要修改此模块。

### 3.5.2 功能列表

| 编号 | 功能 | 优先级 | 说明 |
|------|------|--------|------|
| RT-01 | WebSocket 连接建立 | P0 | 客户端与服务端建立 WebSocket 连接 |
| RT-02 | 消息路由 | P0 | 根据消息类型路由到对应的处理器 |
| RT-03 | 比赛通道订阅 | P0 | 选手订阅特定比赛的消息通道 |
| RT-04 | 事件广播 | P0 | 向比赛中的所有客户端广播事件 |
| RT-05 | 定向推送 | P0 | 向特定客户端推送消息 |
| RT-06 | 心跳检测 | P0 | 维护连接活性 |
| RT-07 | 断线重连 | P0 | 支持客户端断线后重连 |

### 3.5.3 功能详细说明

**RT-01 WebSocket 连接建立**

- 客户端在登录后，通过 JWT Token 建立 WebSocket 连接
- 连接地址：`ws://{host}/ws/tournament?token={jwt}`
- 服务器验证 Token 有效性，建立连接
- 连接失败时客户端自动重试（指数退避）

**RT-03 比赛通道订阅**

- 选手进入比赛房间时，自动订阅该比赛的通道
- 通道标识：`/topic/tournament/{tournamentId}`
- 裁判自动订阅所执法比赛的通道
- 同一通道的消息推送给所有订阅者

**RT-04 事件广播**

- 向比赛通道内的所有订阅者推送消息
- 典型场景：
  - 比赛开始/结束通知
  - 轮次开始/结束通知
  - 倒计时更新
  - 分数更新
  - 题目轮转通知

**RT-05 定向推送**

- 向特定用户推送消息
- 典型场景：
  - 题目分配（不同选手收到不同的题目）
  - 答案反馈（正确/错误）
  - 格子填写冲突通知（第三轮）

## 3.6 题库管理模块

### 3.6.1 模块概述

负责数独题目的导入、存储和检索。题目是比赛的核心数据，题库管理的质量直接影响比赛体验。

> 设计原因：题库独立于比赛引擎，使得题目可以被多场比赛复用（V2 功能），且题目的导入和验证可以在赛前独立完成，不影响比赛进行。

### 3.6.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| PM-01 | 批量导入题目 | P0 | 管理员 | 通过 JSON 格式批量导入题目 |
| PM-02 | 查看题目列表 | P1 | 管理员 | 查看某轮次下的所有题目 |
| PM-03 | 查看题目详情 | P1 | 管理员 | 查看单道题目的完整数据 |
| PM-04 | 删除题目 | P1 | 管理员 | 删除已导入的题目（仅赛前可删） |
| PM-05 | 题目数据校验 | P0 | 系统 | 导入时校验题目数据的完整性和正确性 |

### 3.6.3 功能详细说明

**PM-01 批量导入题目**

- 支持通过 JSON 格式导入题目
- 导入时执行以下校验：
  - 每道题必须有初始棋盘和正确答案
  - 初始棋盘和答案的维度必须为 9x9
  - 初始棋盘中的数字必须与答案一致（初始格子的值不能与答案矛盾）
  - 答案必须是一个有效的数独解（每行、每列、每宫 1-9 不重复）
  - JOC 类型题目必须有关联字母
  - 关联题必须引用已有的前 9 道题的 ID

**题目导入格式（JSON 示例）**

```json
{
  "roundId": 1,
  "puzzles": [
    {
      "type": "JOC",
      "order": 1,
      "initialGrid": [[5,3,0,0,7,0,0,0,0],[6,0,0,1,9,5,0,0,0],...],
      "solution": [[5,3,4,6,7,8,9,1,2],[6,7,2,1,9,5,3,4,8],...],
      "points": 10,
      "letter": "S"
    }
  ]
}
```

> 设计原因：使用 JSON 格式导入是 MVP 阶段最简单的方案。管理员在本地准备 JSON 文件，通过 API 导入。V2 可增加 Excel 导入、在线编辑等更友好的方式。使用 `initialGrid` 和 `solution` 的二维数组表示棋盘，0 表示空格，1-9 表示已填数字，这是最直观的数独棋盘数据表示方式。

**PM-05 题目数据校验**

校验规则：

1. 结构完整性：所有必填字段都存在
2. 棋盘维度：9x9
3. 值范围：0-9（0 表示空格）
4. 一致性：初始棋盘中的非零值必须与答案对应位置一致
5. 答案有效性：每行、每列、每宫包含 1-9 各一次
6. 数量校验：第一轮 10 题，第二轮 16 题，第三轮至少 1 题
7. 关联校验：第一轮前 9 题有 letter 字段，第 10 题有 relatedPuzzleIds

> 设计原因：严格的导入校验可以避免无效题目进入比赛，减少比赛中出现问题的风险。校验在导入时一次性完成，比赛进行中不需要再验证题目数据。

## 3.7 计分系统模块

### 3.7.1 模块概述

负责答案判定和分数计算。选手提交答案后，计分系统验证答案正确性并计算得分。

> 设计原因：计分逻辑独立于比赛引擎，使得计分规则可以独立演进（如增加时间奖励、难度系数等），不影响比赛流程控制。

### 3.7.2 功能列表

| 编号 | 功能 | 优先级 | 角色 | 说明 |
|------|------|--------|------|------|
| SC-01 | 答案判定 | P0 | 系统 | 判定选手提交的答案是否正确 |
| SC-02 | 分数计算 | P0 | 系统 | 根据正确答案计算得分 |
| SC-03 | 分数更新推送 | P0 | 系统 | 分数变更后实时推送 |
| SC-04 | 个人分数查询 | P0 | 选手 | 查看自己在当前比赛中的分数 |
| SC-05 | 队伍分数查询 | P0 | 全部 | 查看队伍在当前比赛中的总分 |
| SC-06 | 第一轮计分 | P0 | 系统 | 九九归一的特殊计分逻辑 |
| SC-07 | 第二轮计分 | P0 | 系统 | 轮转接力的计分逻辑 |
| SC-08 | 第三轮计分 | P0 | 系统 | 齐心协力的计分逻辑 |

### 3.7.3 功能详细说明

**SC-01 答案判定**

- 第一轮（JOC 题目）：判定单个数字是否正确
- 第一轮（关联题）：判定整道数独题是否正确
- 第二轮：判定整道数独题是否正确
- 第三轮：判定整道数独题是否正确

判定逻辑：
- 对于 JOC 题目：比较选手提交的数字与答案中对应位置的数字
- 对于完整数独题：比较选手提交的完整棋盘与标准答案

> 设计原因：JOC 题目只需判定一个数字，这是它的特殊性。完整数独题需要判定整个棋盘。两种判定逻辑不同，但都由同一个「答案判定」功能入口处理，内部根据题目类型分发。

**SC-06 第一轮计分**

- 每道 JOC 题目正确：获得该题的基础分值
- 第 10 题正确：获得该题的基础分值
- 提交错误：0 分，不扣分
- 选手总分 = 所有正确题目分值之和

**SC-07 第二轮计分**

- 每道正确完成的题目：获得该题的基础分值
- 提交错误：0 分
- 未完成的题目：0 分
- 队伍总分 = 所有队员正确题目分值之和

**SC-08 第三轮计分**

- 每道正确完成的题目：全队获得该题的基础分值
- 提交错误：0 分，可以继续作答
- 队伍总分 = 所有正确题目分值之和

### 3.7.4 分数展示规则

| 维度 | 第一轮 | 第二轮 | 第三轮 |
|------|--------|--------|--------|
| 展示维度 | 个人分 | 个人分 + 队伍总分 | 队伍总分 |
| 更新时机 | 每次提交后 | 每次提交后 | 每次提交后 |
| 可见范围 | 自己 + 裁判 | 全队 + 裁判 | 全队 + 裁判 |

> 设计原因：第一轮是个人赛，展示个人分数；第二轮是团队接力赛，展示个人贡献和团队总分；第三轮是团队协作赛，展示团队总分。分数可见范围的差异体现了比赛规则的设计意图——第一轮强调个人能力，第二、三轮强调团队合作。
