# 第九部分：开发建议

## 9.1 推荐开发顺序

### 9.1.1 开发阶段划分

整个 MVP 开发分为 5 个阶段，每个阶段有明确的交付物和验收标准。

```
阶段1：基础设施    ──►  阶段2：赛前管理    ──►  阶段3：比赛引擎
   (2周)                  (2周)                  (3周)
                                                       │
阶段5：集成与部署  ◄──  阶段4：实时同步
   (1周)                  (2周)
```

> 设计原因：阶段划分遵循「先跑通核心流程，再完善细节」的原则。阶段1搭建基础设施，确保前后端能通信；阶段2实现赛前管理，确保能创建比赛；阶段3实现比赛引擎，确保能跑通三轮赛制；阶段4实现实时同步，确保多人在线体验；阶段5集成测试和部署。

---

### 阶段1：基础设施（第 1-2 周）

**目标**：前后端通信跑通，认证可用，数据库可用。

| 序号 | 任务 | 说明 | 优先级 |
|------|------|------|--------|
| 1.1 | 搭建 Spring Boot 项目 | 集成 Spring Security、JPA、WebSocket、Flyway | P0 |
| 1.2 | 搭建 React 项目 | 集成 Vite、TypeScript、TailwindCSS、React Router | P0 |
| 1.3 | 数据库初始化 | 创建所有表结构（Flyway 脚本） | P0 |
| 1.4 | JWT 认证实现 | 登录、Token 生成与验证、角色校验 | P0 |
| 1.5 | 前端登录页 | 登录表单、Token 存储、路由守卫 | P0 |
| 1.6 | 前端 API 客户端 | Axios 封装、统一错误处理 | P0 |
| 1.7 | WebSocket 连接 | 前端 WebSocket 客户端、后端 STOMP 配置 | P0 |
| 1.8 | 统一异常处理 | 后端 GlobalExceptionHandler、前端错误提示 | P1 |

**交付物**：
- 前后端能通信
- 能登录获取 Token
- WebSocket 能连接
- 数据库表结构就绪

**验收标准**：
- 通过 Postman/curl 调用登录 API 获取 Token
- 前端登录后跳转到对应角色页面
- WebSocket 能发送和接收消息

### 阶段2：赛前管理（第 3-4 周）

**目标**：管理员能完成比赛创建、配置、队伍分配的全流程。

| 序号 | 任务 | 说明 | 优先级 |
|------|------|------|--------|
| 2.1 | 用户管理 API | 创建用户、查看用户列表 | P0 |
| 2.2 | 比赛管理 API | CRUD 比赛 | P0 |
| 2.3 | 轮次管理 API | 创建轮次、配置轮次 | P0 |
| 2.4 | 题目管理 API | 批量导入题目、校验 | P0 |
| 2.5 | 队伍管理 API | 创建队伍、分配选手 | P0 |
| 2.6 | 管理员前端页面 | 比赛列表、创建比赛、轮次管理、题目导入、队伍管理 | P0 |
| 2.7 | 数据校验 | 题目数据校验、轮次配置校验 | P0 |

**交付物**：
- 管理员能创建比赛、配置轮次、导入题目、创建队伍、分配选手
- 前端管理后台可用

**验收标准**：
- 通过前端完成完整的赛前配置流程
- 题目导入有校验和错误反馈
- 配置不完整时比赛状态不会变为 READY

### 阶段3：比赛引擎（第 5-7 周）

**目标**：三轮赛制完整流程可跑通。

| 序号 | 任务 | 说明 | 优先级 |
|------|------|------|--------|
| 3.1 | 比赛引擎框架 | GameEngine、状态机、计时器 | P0 |
| 3.2 | 比赛控制 API | 开始、暂停、恢复、结束 | P0 |
| 3.3 | 第一轮引擎 | 九九归一流程、JOC 答题、字母揭示 | P0 |
| 3.4 | 第二轮引擎 | 轮转接力流程、题目轮转调度、即时分配 | P0 |
| 3.5 | 第三轮引擎 | 齐心协力流程、共享棋盘、冲突控制 | P0 |
| 3.6 | 答案判定 | JOC 单格判定、完整棋盘判定 | P0 |
| 3.7 | 计分系统 | 三轮计分逻辑、分数计算和存储 | P0 |
| 3.8 | 数独棋盘组件 | 前端数独棋盘交互组件 | P0 |
| 3.9 | 选手答题界面 | 答题、提交、查看分数 | P0 |
| 3.10 | 裁判控制台 | 控制比赛流程、查看状态 | P0 |

**交付物**：
- 三轮赛制流程可完整执行
- 选手能答题、提交、查看分数
- 裁判能控制比赛

**验收标准**：
- 模拟一场完整比赛（三轮），流程顺畅
- 第二轮题目轮转正确
- 第三轮多人协作填写棋盘无冲突
- 计分正确

> 这是最核心也最复杂的阶段。建议先实现第一轮（最简单），验证引擎框架正确；再实现第三轮（共享棋盘），验证实时同步；最后实现第二轮（最复杂的轮转逻辑）。

## 9.2 MVP 优先级

### 9.2.1 功能优先级矩阵

| 优先级 | 功能 | 不做的后果 |
|--------|------|-----------|
| P0（必须） | 用户登录认证 | 系统无法使用 |
| P0（必须） | 比赛创建与配置 | 无法组织比赛 |
| P0（必须） | 题目导入 | 无法开始比赛 |
| P0（必须） | 三轮赛制流程 | 核心功能缺失 |
| P0（必须） | 服务器计时 | 比赛不公平 |
| P0（必须） | 答案判定与计分 | 比赛无结果 |
| P0（必须） | 实时同步 | 多人体验不可用 |
| P0（必须） | 裁判控制 | 无法控制比赛流程 |
| P1（重要） | 暂停/恢复 | 比赛意外中断无法恢复 |
| P1（重要） | 断线重连 | 网络不稳定选手弃权 |
| P1（重要） | 房间状态监控 | 裁判无法了解比赛状态 |
| P1（重要） | 管理员账号管理 | 依赖数据库手动操作 |
| P2（可选） | 题目删除 | 题目导入错误需重新创建轮次 |
| P2（可选） | 比赛编辑 | 配置错误需重新创建比赛 |
| P2（可选） | 精美 UI | 功能可用但体验粗糙 |

### 9.2.2 P0 功能的开发顺序建议

```
1. 认证（登录/Token/角色校验）
2. 比赛管理（创建比赛、轮次、导入题目）
3. 队伍管理（创建队伍、分配选手）
4. 第一轮引擎（最简单，验证框架）
5. 答案判定与计分
6. 第三轮引擎（验证实时同步）
7. 第二轮引擎（最复杂的轮转逻辑）
8. 实时同步完善（倒计时、事件推送）
9. 裁判控制台
10. 断线重连
```

> 设计原因：这个顺序确保每个步骤完成后都能产生可验证的成果。先做第一轮是因为它最简单，可以验证引擎框架的正确性；先于第三轮做第二轮是错的，因为第三轮的实时同步是第二轮题目轮转推送的基础——先验证实时同步机制可靠，再在第二轮中使用它。

## 9.4 风险分析

### 9.4.1 技术风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 第二轮轮转逻辑复杂，容易出 Bug | 高 | 高 | 提前编写详细单元测试，使用模拟数据验证。开发前先画出完整的轮转状态机，穷举边界场景 |
| 第三轮并发填写冲突处理不当 | 中 | 高 | 采用先到先得策略，实现简单且公平。服务器端统一加锁，保证操作原子性 |
| WebSocket 断线导致选手丢失状态 | 中 | 高 | 实现断线重连 + 状态同步（SS-20 GAME_STATE_SYNC）。关键操作同时支持 REST API 作为后备 |
| 服务器计时精度不够 | 低 | 高 | 使用 ScheduledExecutorService 而非 Timer，精度更可靠。每秒推送而非每毫秒，降低精度要求 |
| 前后端 WebSocket 消息格式不一致 | 中 | 中 | 定义共享的类型文件（TypeScript 接口 + Java DTO），确保两端使用一致的事件格式 |
| 数据库连接池耗尽 | 低 | 中 | 配置合理的连接池大小（HikariCP 默认 10，MVP 足够）。监控连接池使用情况 |

### 9.4.2 业务风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 题目格式不规范导致导入失败 | 高 | 中 | 严格的导入校验 + 清晰的错误反馈。提供题目模板文件 |
| 比赛规则理解偏差导致功能不符合需求 | 中 | 高 | 开发前与赛事方确认规则细节。每个轮次开发完成后组织一次模拟比赛验证 |
| 选手操作失误（误提交等） | 中 | 低 | MVP 不支持撤销。V2 可增加确认弹窗。已提交不可修改是比赛规则 |
| 裁判操作失误（误暂停等） | 低 | 中 | 重要操作增加确认弹窗。暂停和恢复是可逆操作，影响可控 |
| 网络环境差导致比赛体验差 | 中 | 高 | 断线重连机制。倒计时以服务器为准，选手重连后时间不会跳变 |

### 9.4.3 项目风险

| 风险 | 概率 | 影响 | 缓解措施 |
|------|------|------|----------|
| 开发周期超出预期（特别是第二轮） | 高 | 中 | 第二轮优先完成核心轮转逻辑，边界场景后续迭代。如果时间紧张，可简化即时分配逻辑 |
| 前后端联调耗时过多 | 中 | 中 | 早期定义 API 契约（可使用 OpenAPI 文档），前后端并行开发 |
| 测试覆盖不足导致线上 Bug | 中 | 高 | 核心逻辑（计分、轮转、判定）必须有单元测试。每个阶段交付前做一次手动测试 |
| 需求变更 | 低 | 中 | MVP 范围明确，变更需经过评估。模块化设计使变更影响范围可控 |

## 9.5 开发规范建议

### 9.5.1 代码规范

| 规范 | 说明 |
|------|------|
| 后端命名 | 类名 PascalCase，方法名 camelCase，常量 UPPER_SNAKE_CASE |
| 前端命名 | 组件名 PascalCase，函数名 camelCase，常量 UPPER_SNAKE_CASE |
| API 路径 | 全小写，连字符分隔（如 /api/tournaments/{id}/rounds） |
| WebSocket 事件 | UPPER_SNAKE_CASE（如 ROUND_STARTED、CELL_FILL） |
| 数据库表名 | 小写，下划线分隔（如 player_puzzle_assignment） |
| Git 分支 | main（生产）、develop（开发）、feature/*（功能）、hotfix/*（紧急修复） |
| Commit 消息 | feat: / fix: / refactor: / docs: / test: 前缀 |

### 9.5.2 测试规范

| 规范 | 说明 |
|------|------|
| 单元测试 | Service 层核心方法必须有单元测试 |
| 测试命名 | test_方法名_场景_预期结果（如 test_submitAnswer_correctJOC_returnsLetter） |
| 测试数据 | 使用固定测试数据，不依赖数据库状态 |
| 核心测试场景 | 1. 正常流程 2. 边界条件 3. 异常情况 4. 并发场景（第二轮轮转） |

### 9.5.3 API 文档

- 建议使用 SpringDoc（OpenAPI 3.0）自动生成 API 文档
- 前端根据 API 文档开发，不依赖后端代码
- WebSocket 事件文档手动维护（目前没有自动生成工具）

## 9.6 里程碑定义

| 里程碑 | 时间 | 交付物 | 验收方式 |
|--------|------|--------|----------|
| M1：基础可用 | 第2周末 | 前后端通信跑通，认证可用 | 手动测试登录流程 |
| M2：赛前就绪 | 第4周末 | 管理员能完成赛前配置 | 完整赛前配置演示 |

> 设计原因：里程碑定义确保每个阶段有明确的交付和验收标准。M3 是关键里程碑——如果第一轮能跑通，说明引擎框架正确，后续轮次的风险大幅降低。

## 9.7 团队分工建议

### 9.7.1 最小团队配置

| 角色 | 人数 | 职责 |
|------|------|------|
| 后端开发 | 1-2 | Spring Boot 开发、数据库、WebSocket 服务端 |
| 前端开发 | 1-2 | React 开发、UI 组件、WebSocket 客户端 |
| 全栈/测试 | 1 | 集成测试、Bug 修复、文档 |

### 9.7.2 协作要点

1. **API 契约先行**：后端先定义 API 接口和数据格式，前端据此并行开发
2. **WebSocket 事件文档**：维护一份共享的事件文档，前后端按文档实现
3. **每日同步**：前后端开发人员每日同步进度，及时解决接口对接问题
4. **集成频率**：每周至少一次前后端集成，避免积累大量集成问题

## 9.8 关键技术决策备忘

以下决策在开发过程中可能需要重新评估，记录其决策依据以便未来参考：

| 决策 | 当前选择 | 何时重新评估 | 替代方案 |
|------|----------|-------------|----------|
| 状态管理 | Zustand | 前端状态复杂度超出预期时 | Redux Toolkit |
| WebSocket 库 | @stomp/stompjs | Spring WebSocket 兼容性问题时 | SockJS + STOMP |
| 棋盘数据格式 | 二维数组 | 需要增量更新时 | Diff 格式（仅传输变更的格子） |
| 计时实现 | ScheduledExecutorService | 需要更精确计时时 | Netty Timer / Akka Scheduler |
| 格子冲突策略 | 先到先得（服务端判定） | 体验不佳时 | OT（操作转换）/ CRDT |
| 题目存储 | JSONB | 需要大量题目查询时 | 独立字段 + 索引 |

> 设计原因：技术决策不是一成不变的，但每次变更都需要有充分的理由。记录决策依据可以帮助团队在重新评估时理解当初为什么这样选，避免无意义的反复。
