# 第四部分：非功能需求

## 4.1 性能需求

### 4.1.1 响应时间

| 操作 | 目标响应时间 | 说明 |
|------|-------------|------|
| 页面加载 | ≤ 2s | 首次加载，含静态资源 |
| API 请求 | ≤ 500ms | 普通 CRUD 操作 |
| WebSocket 消息延迟 | ≤ 200ms | 服务器处理到客户端收到 |
| 答案提交响应 | ≤ 500ms | 从提交到收到判定结果 |
| 第三轮格子填写同步 | ≤ 300ms | 从填写到其他队员看到 |

> 设计原因：比赛场景对实时性要求高，但 MVP 阶段参赛规模有限（预估单场比赛 10-50 人），以上目标在单服务器部署下即可达成。V2 需要针对更大规模（数百人）重新评估。

### 4.1.2 并发能力

| 指标 | MVP 目标 | V2 目标 |
|------|----------|---------|
| 同时在线选手 | 50 | 500 |
| 同时进行的比赛 | 1 | 10 |
| WebSocket 并发连接 | 100 | 1000 |
| 每秒消息推送量 | 100 条 | 2000 条 |

> 设计原因：MVP 阶段单场比赛规模有限，50 人并发是合理的初始目标。但架构设计需要支持 V2 的扩展目标，通过引入 Redis 和水平扩展实现。

### 4.1.3 计时精度

- 服务器计时精度：秒级
- 倒计时推送频率：每秒 1 次
- 选手端显示误差：≤ 1 秒（网络延迟导致）

> 设计原因：正式数独比赛的计时精度要求为秒级，不需要毫秒级精度。每秒推送一次倒计时在实时性和服务器负载之间取得平衡。如果网络延迟导致选手端计时误差超过 2 秒，客户端应显示服务器推送的时间而非本地估算。

## 4.2 安全需求

### 4.2.1 认证与授权

| 需求 | 说明 | 优先级 |
|------|------|--------|
| JWT Token 认证 | 所有 API 请求必须携带有效 Token | P0 |
| 角色权限控制 | 不同角色只能访问对应权限的 API | P0 |
| Token 过期处理 | Token 过期后客户端跳转到登录页 | P0 |
| WebSocket 认证 | WebSocket 连接时验证 Token | P0 |
| HTTPS | 生产环境必须使用 HTTPS | P1 |

> 设计原因：MVP 阶段的安全需求以「防止未授权访问」为核心。JWT + 角色校验是最简单有效的方案。V2 增加更细粒度的权限控制（如资源级别的 ACL）和安全审计日志。

### 4.2.2 数据安全

| 需求 | 说明 | 优先级 |
|------|------|--------|
| 密码加密存储 | BCrypt 加密 | P0 |
| 题目答案保护 | 答案仅在服务器端使用，不推送给客户端 | P0 |
| 防止答案泄露 | API 返回题目时不含标准答案 | P0 |
| SQL 注入防护 | 使用 JPA 参数化查询 | P0 |
| XSS 防护 | 前端输入转义 + 后端校验 | P0 |

> 设计原因：题目答案是比赛的核心机密数据，必须确保不会通过任何渠道泄露给选手。这是比赛公平性的底线。API 设计时，返回给前端的数据永远不包含 solution 字段。

### 4.2.3 比赛公平性

| 需求 | 说明 | 优先级 |
|------|------|--------|
| 服务器权威计时 | 客户端不能控制比赛时间 | P0 |
| 服务器权威判定 | 答案正确性由服务器判定 | P0 |
| 防止重复提交 | 已提交的答案不能修改 | P0 |
| 防止越权操作 | 选手只能操作自己权限内的功能 | P0 |
| 断线重连保护 | 断线不等于弃权，保留答题状态 | P0 |

> 设计原因：正式比赛的公平性是系统存在的基础。如果选手可以通过客户端篡改时间、答案或状态，整个比赛结果都没有公信力。因此所有关键判定必须在服务器端完成。

## 4.3 可靠性需求

### 4.3.1 可用性

| 指标 | MVP 目标 | 说明 |
|------|----------|------|
| 系统可用性 | 99%（比赛期间） | 比赛期间系统必须可用 |
| 计划外停机 | ≤ 1 小时/月 | 开发阶段宽松要求 |
| 数据丢失 | 0 | 比赛结果数据不可丢失 |

> 设计原因：MVP 阶段的可用性要求相对宽松，因为比赛规模小、频率低。但比赛结果数据是不可丢失的——这是比赛严肃性的体现。

### 4.3.2 容错能力

| 场景 | 处理策略 |
|------|----------|
| 选手网络断开 | 服务器保持状态，支持 5 分钟内重连 |
| 服务器重启 | 比赛状态持久化到数据库，重启后恢复 |
| WebSocket 断开 | 客户端自动重连，重连后同步最新状态 |
| 倒计时推送丢失 | 客户端展示最后一次收到的时间，下次推送时校正 |
| 数据库不可用 | API 返回 503，比赛状态不可变更 |

> 设计原因：网络断开是比赛中常见的异常场景，必须有明确的处理策略。服务器重启是开发阶段可能遇到的情况，状态持久化确保重启后可以恢复。V2 引入 Redis 和集群部署后，单点故障的影响会降低。

### 4.3.3 数据持久化

- 所有比赛配置数据：实时持久化到 PostgreSQL
- 比赛进行中的关键状态变更：实时持久化到 PostgreSQL
  - 答案提交
  - 分数变更
  - 轮次状态变更
  - 题目轮转记录
- WebSocket 连接状态：内存中维护，不持久化
- 倒计时：服务器内存中维护，每次状态变更时持久化剩余时间

> 设计原因：比赛结果数据是核心资产，必须实时持久化。WebSocket 连接是临时状态，不需要持久化。倒计时如果服务器重启，可以从数据库恢复剩余时间继续计时。

## 4.4 可维护性需求

### 4.4.1 代码质量

| 需求 | 说明 |
|------|------|
| 分层架构 | Controller → Service → Repository，职责清晰 |
| 模块化设计 | 每个业务模块独立，通过接口通信 |
| 命名规范 | 统一的命名规范（类名、方法名、变量名） |
| 异常处理 | 统一的异常处理机制，明确的错误码 |
| 日志规范 | 关键操作有日志记录，日志级别合理 |

### 4.4.2 前端可维护性

| 需求 | 说明 |
|------|------|
| 组件化 | UI 拆分为可复用的组件 |
| 状态管理 | 统一的状态管理方案 |
| 样式管理 | TailwindCSS 原子化样式，避免样式冲突 |
| 类型安全 | TypeScript 严格模式，减少运行时错误 |
| 路由管理 | React Router 统一管理路由和权限守卫 |

> 设计原因：前后端都需要注重可维护性。后端分层架构是 Spring Boot 项目的最佳实践，前端组件化和状态管理是 React 项目的标配。这些不是「锦上添花」，而是「必须做到」。

### 4.4.3 UI 可替换性

系统需要支持在不修改业务逻辑的情况下更换整个 UI。实现方式：

1. 前后端完全分离，通过 REST API 和 WebSocket 通信
2. API 契约稳定，不因 UI 变更而修改
3. 前端项目独立，可以整体替换为其他前端框架实现
4. 业务逻辑不依赖前端的任何实现细节

> 设计原因：赛事平台可能需要品牌定制（如不同赛事的不同视觉风格），或者未来迁移到移动端。前后端分离 + 稳定 API 契约使得 UI 替换不影响后端。

## 4.5 可扩展性需求

### 4.5.1 架构可扩展性

| 扩展方向 | 当前架构如何支持 | 实施时机 |
|----------|-----------------|----------|
| 多赛事并行 | 数据模型以 Tournament 为顶级实体 | V2 |
| Redis 缓存 | 状态管理通过抽象接口 | V2 |
| 消息队列 | 事件驱动模型 | V2 |
| 微服务 | 模块化边界清晰 | V3 |
| 水平扩展 | 无状态服务 + 数据库持久化 | V2 |
| 容器化 | 前后端分离 + 无状态 | V2 |

### 4.5.2 业务可扩展性

| 扩展方向 | 说明 | 实施时机 |
|----------|------|----------|
| 新赛制 | 比赛引擎支持注册新的轮次类型处理器 | V2 |
| 新题型 | 题目类型通过枚举扩展，判定逻辑可插拔 | V2 |
| 新角色 | 角色系统支持新增角色和权限配置 | V2 |
| 新计分规则 | 计分系统支持注册新的计分策略 | V2 |

> 设计原因：可扩展性不是 MVP 的实现目标，而是架构的设计约束。以上扩展点通过接口抽象和模块化设计来预留，不需要在 MVP 中实现具体扩展逻辑。关键是在架构层面不设置扩展障碍。

### 4.5.3 MVP 阶段的可扩展性底线

MVP 阶段不需要实现任何扩展功能，但必须满足以下底线：

1. 不在代码中硬编码只能处理 3 个轮次——使用轮次列表
2. 不在代码中硬编码轮次类型——使用枚举或策略模式
3. 不在数据库中混合不同轮次类型的字段——使用通用结构 + 可选字段
4. 不在 API 中暴露内部实现细节——API 设计面向资源，不面向实现
5. 不在模块间创建循环依赖——依赖方向必须是单向的

> 设计原因：这些底线是「低成本高回报」的设计约束——它们几乎不增加 MVP 的开发成本，但可以避免后续重构的高昂代价。

## 4.6 可测试性需求

### 4.6.1 测试策略

| 测试类型 | 范围 | MVP 优先级 | 说明 |
|----------|------|-----------|------|
| 单元测试 | Service 层核心逻辑 | P0 | 计分逻辑、答案判定、轮转逻辑 |
| 集成测试 | API 端到端 | P1 | 主要 API 的正常流程和异常流程 |
| WebSocket 测试 | 实时通信 | P1 | 消息收发、断线重连 |
| 前端组件测试 | 核心组件 | P2 | 棋盘组件、计时器组件 |
| E2E 测试 | 完整比赛流程 | P2 | 三轮赛制的完整流程 |

### 4.6.2 可测试性设计

| 需求 | 说明 |
|------|------|
| 依赖注入 | Spring Boot 原生支持，便于 Mock |
| 接口抽象 | 核心模块通过接口定义契约，便于替换实现进行测试 |
| 时间可控 | 服务器计时使用可注入的 Clock，测试时可控制时间 |
| WebSocket 可测试 | 使用 Spring 的 WebSocket 测试支持 |
| 测试数据 | 提供标准数独题目的测试数据集 |

> 设计原因：比赛引擎的计时、轮转等逻辑依赖时间，如果直接使用 `System.currentTimeMillis()`，测试中将无法控制时间。使用可注入的 Clock 是解决此问题的标准做法。
