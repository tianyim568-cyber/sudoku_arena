# 第二部分：产品需求分析

## 2.1 用户角色

### 2.1.1 角色定义

系统包含三类用户角色，每个角色有明确的职责边界和操作权限。

| 角色 | 代码标识 | 职责描述 | 操作范围 |
|------|----------|----------|----------|
| 管理员 | ADMIN | 赛事的全生命周期管理，包括创建比赛、配置赛制、管理选手和裁判 | 全局 |
| 裁判 | JUDGE | 比赛进行中的流程控制，包括开始、暂停、结束比赛，监控比赛状态 | 单场比赛 |
| 选手 | PLAYER | 参加比赛，答题、提交答案、查看自己状态 | 单场比赛中自己 |

### 2.1.2 角色权限矩阵

| 操作 | 管理员 | 裁判 | 选手 |
|------|--------|------|------|
| 登录系统 | Y | Y | Y |
| 创建比赛 | Y | N | N |
| 创建比赛轮次 | Y | N | N |
| 导入数独题目 | Y | N | N |
| 创建队伍 | Y | N | N |
| 分配选手到队伍 | Y | N | N |
| 分配裁判到比赛 | Y | N | N |
| 开始比赛 | Y | Y | N |
| 暂停比赛 | Y | Y | N |
| 结束比赛 | Y | Y | N |
| 查看比赛状态 | Y | Y | N |
| 查看所有房间状态 | Y | Y | N |
| 进入比赛房间 | N | N | Y |
| 查看题目 | N | N | Y |
| 提交答案 | N | N | Y |
| 查看自己的分数 | N | N | Y |
| 查看比赛倒计时 | N | Y | Y |
| 查看队伍分数 | Y | Y | Y |

> 设计原因：MVP 阶段仅设三种角色，权限边界清晰。管理员负责「赛前准备」，裁判负责「赛中控制」，选手负责「赛中参与」。不存在角色重叠，避免权限混淆。V2 可扩展「观察者」角色（如观众、教练），当前不纳入。

## 2.2 业务流程

### 2.2.1 整体业务流程

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│  赛前准备    │ ──► │  比赛进行    │ ──► │  比赛结束    │ ──► │  结果确认    │
│  (管理员)    │     │  (裁判+选手) │     │  (裁判)      │     │  (全员)      │
└─────────────┘     └─────────────┘     └─────────────┘     └─────────────┘
```

### 2.2.2 赛前准备流程

由管理员完成，是比赛进行的前提条件。

```
1. 管理员登录系统
2. 创建比赛（设置名称、描述、时间）
3. 创建比赛轮次
   ├── 第一轮：九九归一（20分钟，10道题）
   ├── 第二轮：轮转接力（20分钟，16道题）
   └── 第三轮：齐心协力（30分钟，若干题）
4. 导入数独题目
   ├── 导入第一轮题目（9道 JOC + 1道关联题）
   ├── 导入第二轮题目（16道标准题）
   └── 导入第三轮题目（若干标准题）
5. 创建队伍
6. 分配选手到队伍
7. 分配裁判到比赛
8. 赛前准备完成，等待比赛开始
```

> 设计原因：赛前准备是线性流程，每一步都依赖前一步完成。例如必须先有队伍才能分配选手，必须先有轮次才能导入题目。系统需要验证前置条件是否满足。

### 2.2.3 比赛进行流程

由裁判控制节奏，选手参与答题。

```
1. 裁判进入比赛控制台
2. 选手进入比赛房间
3. 所有选手就绪（或裁判手动触发）
4. 裁判开始第一轮
   ├── 服务器推送「第一轮开始」事件
   ├── 服务器开始倒计时（20分钟）
   ├── 选手答题
   ├── 服务器推送倒计时
   ├── 计时结束或所有选手完成
   └── 服务器推送「第一轮结束」事件
5. 裁判开始第二轮
   ├── 服务器推送「第二轮开始」事件
   ├── 服务器开始倒计时（20分钟）
   ├── 题目轮转逻辑执行
   ├── 选手答题
   ├── 服务器推送倒计时和轮转事件
   ├── 计时结束或所有选手完成
   └── 服务器推送「第二轮结束」事件
6. 裁判开始第三轮
   ├── 服务器推送「第三轮开始」事件
   ├── 服务器开始倒计时（30分钟）
   ├── 所有队员共享空间，实时同步
   ├── 选手答题
   ├── 服务器推送倒计时和实时状态
   ├── 计时结束或所有选手完成
   └── 服务器推送「第三轮结束」事件
7. 裁判结束比赛
8. 服务器推送「比赛结束」事件和最终结果
```

> 设计原因：三轮比赛是串行执行的，每轮独立计时。裁判控制轮次间的切换，而非自动跳转。这是正式比赛的惯例——裁判需要确认选手状态后再开始下一轮。

### 2.2.4 比赛结束流程

```
1. 最后一轮计时结束，或裁判手动结束比赛
2. 服务器停止所有计时器
3. 服务器计算最终分数
4. 服务器推送「比赛结束」事件 + 最终分数
5. 所有选手看到最终结果
6. 裁判确认比赛完成
```

## 2.3 比赛流程详解

### 2.3.1 第一轮：九九归一

**基本信息**

| 属性 | 值 |
|------|-----|
| 回合名称 | 九九归一 |
| 比赛时间 | 20 分钟 |
| 题目数量 | 10 道 |
| 参赛方式 | 个人独立答题 |
| 题目类型 | 前9道为 Just One Cell，第10道为关联题 |

**流程详解**

```
比赛开始
    │
    ▼
┌─────────────────────────────────────────────┐
│  选手收到 9 道 Just One Cell 题目           │
│  每道题只能推出一个数字                      │
│  每道题的答案对应一个字母                    │
│  9 个字母组成第 10 题的线索信息             │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  选手逐题作答                               │
│  可以按任意顺序作答                          │
│  每完成一题，系统确认答案并揭示对应字母      │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  选手收集完 9 个字母后                      │
│  根据字母信息解答第 10 题                   │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  提交第 10 题答案                           │
│  或计时结束                                 │
└─────────────────────────────────────────────┘
    │
    ▼
  第一轮结束
```

**关键规则**

1. 每道 Just One Cell 题目只有一个正确答案（一个数字），选手填入该数字后即可获得对应字母。
2. 9 个字母的获取顺序不影响第 10 题的解答——无论选手先做哪道题，最终都获得相同的 9 个字母。
3. 第 10 题需要利用 9 个字母组合得到的信息来解题，字母的正确获取是解答第 10 题的前提。
4. 选手必须先正确回答前 9 题中的某一题，才能获得对应字母。未获得字母不影响其他题目的作答，但影响第 10 题的解答。
5. 计时 20 分钟，到时自动结束。

**计分规则**

| 项目 | 分值 | 说明 |
|------|------|------|
| 每道 Just One Cell 正确 | 基础分 | 答对得分 |
| 第 10 题正确 | 加分 | 完成关联题的额外分数 |
| 提交错误 | 0 分 | 不扣分，但不计分 |

> 设计原因：九九归一是一种「线索聚合」题型，前 9 题的答案不是独立的——它们共同构成第 10 题的必要信息。这种设计鼓励选手尽量完成所有题目，而不是只做部分。MVP 阶段计分规则保持简单（正确得分，错误不得分），后续版本可增加时间奖励等复杂规则。

### 2.3.2 第二轮：轮转接力

**基本信息**

| 属性 | 值 |
|------|-----|
| 回合名称 | 轮转接力 |
| 比赛时间 | 20 分钟 |
| 题目数量 | 16 道 |
| 参赛方式 | 团队接力，每队 4 人 |
| 题目类型 | 标准数独 |

**流程详解**

```
比赛开始
    │
    ▼
┌─────────────────────────────────────────────┐
│  每队 4 名队员各获得 1 道不同的题目         │
│  队员 A → 题目 1                            │
│  队员 B → 题目 2                            │
│  队员 C → 题目 3                            │
│  队员 D → 题目 4                            │
│  剩余 12 道题在题池中等待分配              │
└─────────────────────────────────────────────┘
    │
    ├──── 队员提前完成题目 ────┐
    │                          │
    │    ┌─────────────────────┘
    │    ▼
    │  立即提交
    │    │
    │    ▼
    │  系统自动分配题池中下一道未完成的题
    │    │
    │    ▼
    │  继续答题
    │
    ├──── 每隔 1 分钟 ─────────┐
    │                          │
    │    ┌─────────────────────┘
    │    ▼
    │  所有未完成题目轮转给下一位队员
    │  （队员 A 的未完成题 → 队员 B）
    │  （队员 B 的未完成题 → 队员 C）
    │  （队员 C 的未完成题 → 队员 D）
    │  （队员 D 的未完成题 → 队员 A）
    │    │
    │    ▼
    │  继续答题
    │
    ▼
┌─────────────────────────────────────────────┐
│  计时 20 分钟结束                           │
│  统计每队总分                               │
└─────────────────────────────────────────────┘
    │
    ▼
  第二轮结束
```

**关键规则**

1. 题目轮转是按固定顺序的：A→B→C→D→A→B→...，每分钟轮转一次。
2. 队员提前完成当前题目并提交后，系统立即从题池中分配下一道未完成的题。如果题池为空且没有其他队员正在做的未完成题，则该队员等待。
3. 已经提交的题目不能再次修改，答案一旦提交即锁定。
4. 队员之间禁止交流。这是比赛规则约束，MVP 不需要实现聊天功能，也不需要技术手段阻止交流。
5. 轮转时，正在进行的题目状态（已填入的数字）保留，下一位队员看到的是上一位队员的进度。
6. 计时 20 分钟，到时自动结束。

**题目轮转机制详解**

```
时间轴：

T=0min    A:题1  B:题2  C:题3  D:题4  [题池: 题5~16]

T=1min    轮转！
          A:题4* B:题1* C:题2* D:题3*  [题池: 题5~16]
          （带*表示从上一位队员轮转来的，保留已有填写状态）

T=2min    轮转！
          A:题3* B:题4* C:题1* D:题2*  [题池: 题5~16]

...如果队员 A 在 T=1.5min 完成了题4...
          A:题5  B:题1* C:题2* D:题3*  [题池: 题6~16]
          （A 提交题4，系统从题池分配题5）

T=2min    轮转！
          如果题5未完成，轮转给 B
          A:等待  B:题5* C:题1* D:题2*  [题池: 题6~16]
          （A 没有未完成题，分配题池中下一题：题6）
          A:题6  B:题5* C:题1* D:题2*  [题池: 题7~16]
```

> 设计原因：轮转接力是最复杂的赛制，核心挑战是「题目轮转」和「即时分配」两个并发逻辑。轮转按固定周期执行（每分钟），即时分配是事件驱动的（提交即分配）。这两个逻辑可能同时触发，需要明确定义优先级：提交分配优先于轮转。即如果队员在轮转前一刻提交了题目，该题已标记为完成，不参与轮转。

**计分规则**

| 项目 | 分值 | 说明 |
|------|------|------|
| 每道正确题目 | 基础分 | 答对得分 |
| 提交错误 | 0 分 | 不扣分 |
| 未完成 | 0 分 | 计时结束时未提交的题 |

### 2.3.3 第三轮：齐心协力

**基本信息**

| 属性 | 值 |
|------|-----|
| 回合名称 | 齐心协力 |
| 比赛时间 | 30 分钟 |
| 题目数量 | 若干道 |
| 参赛方式 | 团队协作，所有成员共享同一空间 |
| 题目类型 | 标准数独 |
| 实时同步 | 是 |

**流程详解**

```
比赛开始
    │
    ▼
┌─────────────────────────────────────────────┐
│  所有队员进入同一比赛空间                    │
│  看到同一道数独题                           │
│  所有成员可以填写任何空格                    │
│  实时同步所有人的操作                        │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  队员 A 填入数字 → 实时同步到所有队员       │
│  队员 B 填入数字 → 实时同步到所有队员       │
│  ...                                        │
│  所有队员看到的是同一棋盘的最新状态         │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  某队员提交完整答案                         │
│  系统判定正确 → 进入下一题                  │
│  系统判定错误 → 提示错误，继续填写          │
└─────────────────────────────────────────────┘
    │
    ▼
┌─────────────────────────────────────────────┐
│  计时 30 分钟结束                           │
│  统计每队完成题目数量和总分                  │
└─────────────────────────────────────────────┘
    │
    ▼
  第三轮结束
```

**关键规则**

1. 所有队员共享同一个数独棋盘，任何人的填写操作都实时同步给其他队员。
2. 需要处理并发填写冲突：当两名队员同时填写同一个格子时，以先到达服务器的操作为准，后到的操作被拒绝并通知该队员。
3. 提交可以由任何队员触发，提交后系统判定整道题的正确性。
4. 正确则进入下一题，错误则继续当前题目。
5. 计时 30 分钟，到时自动结束。

**实时同步机制**

```
队员 A 填入 R3C5=7
        │
        ▼
    服务器验证
        │
        ├── 有效 → 广播给所有队员：R3C5=7
        │          队员 A 的界面：显示已填入
        │          队员 B 的界面：实时显示 R3C5=7
        │
        └── 冲突（R3C5 已被其他队员填入）→ 通知队员 A：R3C5 已被占用
                                              队员 A 的界面：恢复为已填入的值
```

> 设计原因：齐心协力的核心挑战是多人实时编辑同一棋盘的冲突控制。采用「先到先得」策略是比赛场景下最公平的方案——谁先提交谁有效，后到的需要重新选择。这种策略实现简单、判定明确，不会产生歧义。MVP 阶段不需要实现更复杂的协同编辑算法（如 OT 或 CRDT），因为数独棋盘的每个格子是独立的，不存在跨格子的操作依赖。

**计分规则**

| 项目 | 分值 | 说明 |
|------|------|------|
| 每道正确完成的题目 | 基础分 | 全队得分 |
| 提交错误 | 不扣分 | 可以继续填写 |

## 2.4 系统流程

### 2.4.1 用户认证流程

```
用户访问系统
    │
    ▼
输入用户名和密码
    │
    ▼
服务器验证凭据
    │
    ├── 成功 → 返回 JWT Token + 用户信息（角色、ID等）
    │          前端存储 Token
    │          根据 role 跳转到对应界面
    │          ├── ADMIN → 管理后台
    │          ├── JUDGE → 裁判控制台
    │          └── PLAYER → 选手界面
    │
    └── 失败 → 提示错误信息，返回登录页
```

> 设计原因：MVP 阶段使用简单的 JWT 认证。管理员预先创建账号并分配角色，不需要注册和找回密码功能。Token 包含用户 ID 和角色信息，后端通过 Spring Security 进行角色校验。

### 2.4.2 选手参赛流程

```
选手登录
    │
    ▼
查看可参加的比赛列表
    │
    ▼
进入比赛房间（等待比赛开始）

    ▼
裁判开始比赛
    │
    ▼
┌─────────────────────────────────────────────┐
│  比赛进行中                                 │
│  ├── 接收服务器推送的题目                    │
│  ├── 填写答案                               │
│  ├── 提交答案                               │
│  ├── 接收服务器推送的分数更新                │
│  └── 接收服务器推送的倒计时                  │

    │
    ▼
比赛结束，查看结果
```

## 2.6 主要模块

### 2.6.1 模块总览

```
┌─────────────────────────────────────────────────────────────┐
│                     数独比赛管理平台                         │
├─────────┬──────────┬──────────┬──────────┬─────────────────┤
│ 用户管理 │ 比赛管理  │ 比赛引擎 │ 房间管理 │ 题库管理 │ 计分系统 │
└─────────┴──────────┴──────────┴──────────┴─────────────────┘
                           │
                    ┌──────┴──────┐
                    │  实时同步层  │
                    │ (WebSocket)  │
                    └─────────────┘
```

### 2.6.2 模块职责

| 模块 | 职责 | 核心能力 | 依赖 |
|------|------|----------|------|
| 用户管理 | 用户认证与授权 | 登录、角色校验、Token 管理 | 无 |
| 比赛管理 | 比赛配置与组织 | CRUD 比赛、轮次、队伍、选手 | 用户管理、题库管理 |
| 比赛引擎 | 比赛流程执行 | 三轮赛制流程控制、计时、轮转逻辑 | 比赛管理、房间管理、计分系统、实时同步 |
| 房间管理 | 比赛空间管理 | 房间创建、选手分配、状态维护 | 用户管理 |
| 实时同步 | 实时状态推送 | WebSocket 连接管理、事件广播 | 无 |
| 题库管理 | 题目数据管理 | 题目导入、存储、检索 | 无 |
| 计分系统 | 答案判定与计分 | 答案验证、分数计算、分数推送 | 题库管理 |

> 设计原因：模块划分遵循「单一职责」和「高内聚低耦合」原则。每个模块有明确的职责边界，模块间通过接口通信而非直接依赖实现。比赛引擎是核心模块，协调其他模块完成比赛流程，但本身不实现具体细节（如计分、实时推送），而是委托给对应模块。
