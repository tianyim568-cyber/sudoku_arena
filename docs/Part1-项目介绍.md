# 第一部分：项目介绍

## 1.1 项目背景

数独竞技运动在全球范围内持续发展，越来越多的官方数独比赛需要专业的赛事管理系统来支撑。然而，现有的在线数独平台主要面向个人练习和休闲娱乐，缺乏对正式比赛流程的支持。这些平台无法满足以下核心比赛需求：

1. **多回合制比赛流程控制**：正式数独比赛通常包含多个不同规则的回合，每个回合有不同的题型、计时规则和协作方式，现有平台无法统一管理。
2. **实时多人同步**：团队赛中，多名选手需要在同一时间窗口内协同或接力完成题目，要求毫秒级的实时状态同步。
3. **精确的裁判控制**：正式比赛需要裁判能够控制比赛的开始、暂停、结束，且所有计时必须以服务器为唯一权威来源。
4. **特殊题型的流程编排**：如「九九归一」中的线索关联、「轮转接力」中的题目轮转，这些特殊赛制无法用普通答题系统实现。

因此，我们需要一套专门为正式数独比赛设计的实时多人在线比赛管理平台，而非一个练习工具或休闲游戏网站。

## 1.3 系统定位

本系统的定位是：**面向官方数独比赛的实时多人在线比赛管理平台**。

关键定位要素：

1. **比赛管理系统**，不是练习平台。核心价值在于比赛流程的编排、控制和实时同步，而非题库练习。
2. **实时多人**，不是单人做题。系统必须支持多名选手同时在线、实时交互、状态同步。
3. **官方比赛**，不是休闲游戏。系统必须保证比赛的公平性、权威性和流程规范性。
4. **管理平台**，不是单纯的答题界面。系统必须提供完整的管理后台，支持管理员和裁判对比赛的全流程管控。

与现有产品的差异化：

| 维度 | 普通数独网站 | 本系统 |
|------|-------------|--------|
| 核心场景 | 个人练习 | 官方比赛 |
| 用户关系 | 独立答题 | 多人实时协作/竞争 |
| 流程控制 | 自由开始/结束 | 裁判统一控制 |
| 计时方式 | 客户端计时 | 服务器权威计时 |
| 题型支持 | 标准数独 | 多种特殊赛制 |
| 实时性 | 无要求 | 毫秒级同步 |
| 结果权威性 | 娱乐性质 | 比赛正式结果 |

## 1.4 设计原则

### 1.4.1 核心设计原则

**原则一：MVP 优先**

所有功能决策都基于一个问题：「这个功能是比赛必须的吗？」如果不是，就不纳入 MVP。但这不意味着架构短视——MVP 功能最少，但架构设计必须面向未来。

> 设计原因：资源有限，必须先验证核心价值。但架构层面的决策成本远低于重构成本，因此架构需要一步到位。

**原则二：服务器权威**

所有影响比赛结果的状态变更都必须由服务器判定和驱动。客户端是展示层和输入层，不是决策层。

> 设计原因：比赛公平性是底线。任何客户端可篡改的数据都不能作为比赛依据。

**原则三：实时同步优先**

比赛场景下的用户体验高度依赖实时性。选手看到的计时、题目状态、队友进度必须与其他所有参与者一致。

> 设计原因：延迟或不一致会直接导致比赛争议，损害平台公信力。

**原则四：前后端分离**

前端负责 UI 展示和用户交互，后端负责业务逻辑和数据持久化。两者通过 REST API 和 WebSocket 通信，前端可以整体替换而不影响后端逻辑。

> 设计原因：数独比赛平台的 UI 可能需要频繁调整（赛事品牌定制、不同终端适配），前后端分离保证业务逻辑不受 UI 变更影响。

**原则五：模块化高内聚低耦合**

每个功能模块应该有清晰的职责边界。模块之间通过定义良好的接口通信，不直接依赖彼此的内部实现。

> 设计原因：比赛规则可能变化（新赛制、新题型），模块化设计使修改影响范围可控。

**原则六：简单优于灵活**

当存在多个技术方案时，选择最简单、最容易理解和维护的方案。不为假设的未来需求引入不必要的抽象。

> 设计原因：MVP 阶段过度设计比设计不足更危险。简单的系统容易理解、容易调试、容易扩展。

### 1.4.2 设计原则优先级

当原则之间产生冲突时，按以下优先级取舍：

1. 服务器权威（公平性底线）
2. MVP 优先（资源约束）
3. 实时同步优先（核心体验）
4. 简单优于灵活（工程实践）
5. 前后端分离（架构健康）
6. 模块化（可维护性）

## 1.6 未来扩展方向

以下扩展方向在架构设计中已预留能力，但不纳入 MVP 实现。

### 1.6.1 短期扩展（V2）

- **多赛事并行**：当前架构通过 `Tournament` 实体的存在，天然支持多赛事数据隔离。V2 需要增加赛事调度和资源隔离能力。
- **缓存层（Redis）**：当前架构中实时状态通过内存管理，V2 引入 Redis 作为分布式缓存和会话存储，支持水平扩展。
- **消息通知**：当前仅 WebSocket 推送，V2 增加邮件、短信等通知渠道。架构中的事件驱动模型为通知扩展提供了基础。
- **排行榜**：当前仅展示当前比赛分数，V2 增加跨赛事排行榜。计分系统已模块化，新增排行榜模块不影响现有逻辑。
- **历史比赛统计**：当前比赛数据已持久化，V2 增加查询和展示接口。

### 1.6.2 中期扩展（V3）

- **容器化部署（Docker）**：前后端已分离，容器化只需增加 Dockerfile 和编排配置。
- **微服务拆分**：当前模块化设计（比赛引擎、题库、计分、用户）天然对应微服务边界。V3 通过 API Gateway 统一入口，逐步拆分。
- **消息队列**：当前事件通过 WebSocket 直推，V3 引入消息队列解耦事件生产与消费，提升可靠性。
- **社交功能**：新增独立模块，不影响比赛核心流程。
- **AI 辅助**：新增独立模块，作为题库管理的增强工具。

### 1.6.3 长期扩展（V4+）

- **Kubernetes 编排**：基于 Docker 化的基础上，增加 K8s 编排和自动伸缩。
- **多赛事调度引擎**：支持大规模赛事的自动调度、负载均衡和资源分配。
- **国际化**：前端已支持 i18n 友好的文本外置架构，V4 增加多语言支持。
- **开放 API**：为第三方集成提供标准化 API。

### 1.6.4 架构扩展能力说明

| 扩展方向 | 当前架构如何支持 |
|----------|-----------------|
| 多赛事并行 | 数据模型以 Tournament 为顶级实体，所有业务数据关联到具体赛事，天然支持数据隔离 |
| Redis 缓存 | 实时状态管理通过抽象的 StateService 接口，V2 实现 Redis 版本即可替换内存版本 |
| 微服务 | 模块化设计确保每个业务模块有清晰的 API 边界，拆分时只需将模块独立部署 |
| 消息队列 | 事件驱动模型中，事件的发布和消费已解耦，引入消息队列只需替换传输层 |
| 排行榜 | 计分系统独立模块，排行榜模块可并行开发，通过事件订阅获取分数变更 |
| 容器化 | 前后端分离 + 无状态服务设计，容器化无需架构调整 |
| 水平扩展 | 无状态服务 + 数据库持久化，V2 引入 Redis 后支持 Session 共享和水平扩展 |
